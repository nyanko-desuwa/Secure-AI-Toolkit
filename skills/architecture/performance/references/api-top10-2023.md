# OWASP API Security Top 10 (2023) for Resource Lifetime

Verified 2026-07-28 against
<https://owasp.org/API-Security/editions/2023/en/0x11-t10/>.

Use this reference whenever the surface is REST, GraphQL, gRPC, a webhook, or a streaming
endpoint.

## API4:2023 - Unrestricted Resource Consumption

This is the primary API citation for the performance skill. It asks what stops one caller from
exhausting CPU, memory, storage, file descriptors, processes, connections, or paid third-party
quota.

Controls in scope:

| Input-controlled cost | Required bound |
|---|---|
| Request payload | Bytes received, before parsing |
| Upload / archive | Compressed and decompressed bytes, entry count |
| Page / export | Records and response bytes |
| Query | Depth, complexity, execution time |
| Fan-out | Concurrent calls and total work items |
| Queue | Depth and full behaviour |
| Retry | Attempts, total time, idempotency |
| Third-party call | Timeout, concurrency, quota budget |

A gateway body limit does not replace an application bound. Internal callers, alternate routes,
and decompression can bypass or multiply what the gateway measured. Apply limits at each layer
that allocates.

## API6:2023 - Unrestricted Access to Sensitive Business Flows

API4 and API6 are not interchangeable. API4 is resource exhaustion: a million-row page or an
unbounded upload. API6 is valid use at harmful business scale: bulk account creation, ticket
buying, or scraping.

Rate limiting helps both but does not fully solve API6. This skill covers the resource side.
Flow-level abuse controls belong to API and threat-model guidance.

## API1:2023 - Broken Object Level Authorization

A shared cache can turn a resource control into an authorization bug:

```text
report:{report_id}             vulnerable across tenants
report:{tenant_id}:{report_id} identity participates in the cache key
```

If one actor receives another actor's cached object, report API1 and A01:2025. Do not bury it
under performance.

## GraphQL

API4 shifts to query depth and complexity. Bound both. Depth alone misses a wide query with
thousands of sibling fields; complexity alone can miss recursive resolver behaviour if weights
are wrong.

Batched queries multiply cost. Count operations or calculated complexity, not HTTP requests.
Pagination limits still apply per resolver, and a field resolver that emits an unbounded list
can exhaust memory even when the top-level query is cheap.

## Streaming

A streaming endpoint is bounded only if backpressure reaches the producer. A response stream
whose `write()` result is ignored is an unbounded queue hidden inside the transport. When the
client disconnects, cancellation must close the cursor, subscription, and timer.

For uploads, count bytes actually read. `Content-Length` is attacker supplied and can be absent
with chunked transfer encoding.

## Reporting Questions

For every API finding answer:

1. What resource grows?
2. What request value or client behaviour drives it?
3. What is the server-side maximum?
4. What happens when full: block, drop, reject, or time out?
5. Is the event observable and alertable?
6. Does the fix preserve tenant isolation?

Weak: "add rate limiting".

Strong: "cap `limit` at 200 records server-side, reject larger values with 400, and use a
cursor. The current value is client-controlled and materializes the full result in memory.
API4:2023, CWE-770."

## Limitations

- API4 says a limit is needed. It does not choose a correct number for this deployment.
- Rate limiting by IP alone is weak behind shared networks and IPv6 rotation. Actor and flow
  identity may also be needed.
- A bounded response can still be CPU-expensive. Profile resolver and query-plan cost.
- A 503 with `Retry-After` is suitable for transient saturation, not for permanently invalid
  oversized input; use 400 or 413 for that.
