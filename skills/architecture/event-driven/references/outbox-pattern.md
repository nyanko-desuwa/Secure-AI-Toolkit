# Transactional Outbox and At-Least-Once Delivery

Source: microservices.io, Transactional Outbox pattern. Read 2026-07-28.

Cited in this skill for the dual-write problem (E4, E6) and for why idempotency is mandatory
rather than defensive. This file records what the source actually says, separated from what this
skill adds.

## The problem, as stated by the source

A service must change data and emit a message about that change. Two-phase commit across the
database and the broker is unavailable or undesirable. That leaves two broken orderings:

- Publish inside the transaction, then the transaction rolls back. The event describes a state
  that does not exist. Consumers act on a fact that never happened.
- Commit, then publish, then crash between the two. The state changed and nobody was told. The
  read model, the billing service, and the audit trail are permanently wrong, and nothing errors.

The source frames the question as: "How to atomically update the database and send messages to a
message broker?"

Ordering is part of the problem too. Events must reach the broker in the sequence the service
produced them, including when several instances update the same aggregate.

## The solution, as stated

Persist the message in the database inside the same transaction that modifies the business
entities. A separate process ships it to the broker.

Participants: the sender, the database, the message outbox (a table in a relational store, or a
field on each record in a document store), and the message relay. The relay can be built with
transaction log tailing or with a polling publisher.

Benefits the source lists: 2PC is avoided; messages are published exactly when the transaction
commits and not otherwise; and the broker preserves "the order they were sent by the application".

Drawback the source lists, verbatim and as a single item:

> "Potentially error prone since the developer might forget to publish the message/event after
> updating the database."

The source separately notes that delivery is at-least-once: the relay may crash after publishing
but before recording that it published, so consumers must be idempotent - for example by tracking
already-processed message IDs. It observes that this is rarely a burden, since brokers can
duplicate deliveries anyway.

## What this skill adds

Three things the source does not cover, which matter for a security review.

The outbox is not an authorization control. It fixes atomicity between the state change and the
publish. It says nothing about whether the consumer should trust the event's contents. An outbox
row is still just a row somebody wrote; the consumer still re-authorizes (E1).

The outbox table is a growth surface. It accumulates one row per event and is written on the hot
path of every business transaction. Without a delete-or-archive job and an index on the published
marker, the relay's claim query degrades and the table grows without limit. That is CWE-770 by the
same mechanism as any other unbounded store. Two operational details:

- The relay must claim rows so two instances do not publish the same batch. In PostgreSQL,
  `SELECT ... FOR UPDATE SKIP LOCKED`. Without it, concurrent relays double-publish, and now the
  duplicate rate depends on how many relay pods are running.
- The retention decision is a data-protection decision, not a housekeeping one. If the payload
  holds personal data, the outbox is a second copy of it with its own lifetime, sitting in your
  primary database (ASVS V14).

The relay is a deployment artefact, and its absence is invisible from source. A correct outbox
table with no relay deployed is worse than no outbox at all: the code looks right, the
transactions commit, and no event ever leaves. This skill's troubleshooting file lists it as an
unverifiable-from-source claim for that reason. Do not report "the outbox is correct" from reading
the migration and the repository.

## What at-least-once actually obliges you to do

The source's phrasing - "rarely a burden" - is true of the mechanism and understates the code. The
obligation is specific:

- Every handler needs a dedupe key that is stable across redeliveries. The broker's message ID is
  not always that; a republish from the relay after a crash can produce a new broker-side ID for
  the same logical event. Use an event ID generated by the producer and written into the outbox
  row.
- The dedupe claim and the side effect commit in one transaction. A `SELECT` for the key followed
  by an `INSERT` is a time-of-check-time-of-use race, and two concurrent consumers will both pass
  the check (CWE-367 territory; see the CQRS skill, which owns that mapping).
- The dedupe store needs a TTL longer than the maximum redelivery window, which is the broker's
  retention period rather than its visibility timeout. And it needs a TTL at all - see the
  key-store growth hazard in this skill's E9 material. When the dedupe key is user-controlled,
  a missing TTL is an attacker-driven exhaustion vector, not only a leak.
- Side effects that are not idempotent by nature - sending an email, calling a payment API -
  need the idempotency key pushed down to the provider, or a record written before the call and
  checked after. "The handler is idempotent" is false if the third-party call is not.

## Exactly-once

The source does not claim exactly-once, and neither does this skill. Across a broker and an
external side effect there is no protocol that delivers it: the handler can always crash between
performing the effect and acknowledging. What is achievable is at-least-once delivery plus an
idempotent effect, which is observationally equivalent for the caller and is what the code in
`best-practices.md` implements.

Kafka's transactional producer gives exactly-once semantics for a read-process-write cycle whose
input, output, and offsets are all inside Kafka. That is a real guarantee with a narrow domain.
The moment the handler writes to a database or calls an HTTP endpoint, it no longer applies. A
design document that says "exactly-once via Kafka transactions" while the handler charges a card
is wrong, and the failure shows up as a double charge.

## Alternatives named by the source

Event sourcing is listed as an alternative approach: if the event log is the source of truth,
there is no dual write to reconcile. Related patterns are saga and domain event, both of which
create the need in the first place.

Change data capture - log tailing rather than polling - is the same pattern with a different
relay. It removes the polling load and adds an operational dependency, and it publishes whatever
the table contains, which means column-level minimisation becomes the only payload control you
have. If the table has a `password_hash` column and the connector is configured for all columns,
that column is now on the topic (E2).
