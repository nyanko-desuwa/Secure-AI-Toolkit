# OWASP Top 10 2025 - A09 Security Logging and Alerting Failures

> Verified 2026-07-28 against
> <https://owasp.org/Top10/2025/A09_2025-Security_Logging_and_Alerting_Failures/>

## What changed from 2021

The 2021 name was Security Logging and Monitoring Failures. 2025 renames it to Security
Logging and Alerting Failures. The category stayed at position #9; it was voted in from the
community survey rather than driven by data, for the third consecutive edition.

The rename is the substance. Monitoring is a dashboard someone might look at. Alerting is a
notification that reaches a human with a playbook. The category text is explicit that the
change is "to emphasize the alerting function needed to induce action on relevant logging
events."

Do not read the position as low priority. OWASP notes this category "will always be
underrepresented in the data" - it is nearly untestable from outside and carries only 723
CVEs, because a missing log does not produce a CVE.

## Mapped CWEs

Five, as published:

| CWE | Title | Where it bites |
|---|---|---|
| CWE-117 | Improper Output Neutralization for Logs | Newline and control-character injection forging entries |
| CWE-221 | Information Loss of Omission | Events dropped or filtered so the record is incomplete |
| CWE-223 | Omission of Security-relevant Information | The entry exists but lacks the field that would make it useful |
| CWE-532 | Insertion of Sensitive Information into Log File | Passwords, tokens, PII in the log |
| CWE-778 | Insufficient Logging | The event was never emitted |

CWE-221 and CWE-223 are the pair people skip. An entry saying "access denied" with no actor
and no target is CWE-223: the log exists, the investigation still cannot proceed.

## The conditions OWASP lists

Paraphrased from the category description. Each is a checkable condition, which is why this
list is more useful than the title:

- Auditable events - logins, failed logins, high-value transactions - not logged, or logged
  inconsistently. The named example: logging successful logins but not failed attempts
- Warnings and errors producing no, inadequate, or unclear messages
- Log integrity not protected from tampering
- Application and API logs not monitored for suspicious activity
- Logs stored only locally and not backed up
- No effective alerting thresholds or response escalation. Alerts not received or reviewed in
  reasonable time
- DAST scans (Burp, ZAP) against the application trigger no alerts
- No ability to detect, escalate, or alert on active attacks in real or near-real time
- Logging and alerting events visible to a user or attacker - which folds back into
  A01:2025 Broken Access Control - or sensitive data logged that should not be
- Log data not correctly encoded, allowing injection into the logging or monitoring system
- Missing or mishandled errors, so the system is unaware an error occurred and cannot log it
- Alert use cases missing or outdated, so a special situation is not recognised
- So many false positives that real alerts are lost - described as physical overload of the
  SOC team
- Alerts that cannot be actioned because the playbook is incomplete, outdated, or absent

Note the last three. Three of fourteen conditions are about alert quality, not log presence.
A codebase can pass every logging check and still be in this category.

The DAST condition is a free self-test: run ZAP or Burp against a staging environment and see
whether anything fires. If nothing does, the answer to "would we detect an attack" is no.

## Prevention, as published

Grouped by who owns it. Developer-side:

- Log all login, access control, and server-side input validation failures with enough user
  context to identify a suspicious account, retained long enough for delayed forensics
- Log every part of the application containing a security control, on success and failure
- Generate logs in a format a log management solution can consume
- Encode log data correctly to prevent injection into the logging or monitoring system
- Give all transactions an audit trail with integrity controls against tampering or
  deletion - append-only database tables or similar
- Roll back and restart any transaction that throws an error. Always fail closed
- Alert when the application or its users behave suspiciously

Ops-side:

- DevSecOps and security teams establish monitoring and alerting use cases with playbooks so
  the SOC detects and responds quickly
- Add honeytokens as traps - a fake database row, a fake technical user identity. They are
  never touched in normal business, so any access alerts with nearly no false positives
- Behaviour analysis and AI as an optional technique for reducing false positive rates
- Adopt an incident response and recovery plan such as NIST 800-61r2 or later, and teach
  developers what an application attack looks like so they can report it

The honeytoken recommendation is the highest-signal item on the list and the cheapest to
implement. A row in the users table that no code path reads, with an alert on any read.

## Example scenarios, as published

1. A children's health plan provider could not detect a breach for lack of monitoring and
   logging. An external party informed them an attacker had accessed and modified thousands
   of sensitive health records of more than 3.5 million children. Post-incident review found
   the breach could have been in progress since 2013 - more than seven years.
2. A major Indian airline suffered a breach exposing more than ten years of passenger
   personal data, including passport and credit card data. It occurred at a third-party cloud
   hosting provider, who notified the airline some time after.
3. A major European airline had a GDPR-reportable breach, reportedly through payment
   application vulnerabilities, harvesting more than 400,000 customer payment records. The
   privacy regulator fined it 20 million pounds.

Scenario 1 is the one to quote in a design review. Seven years of undetected modification is
not a logging gap, it is the absence of a control.

## Tooling named in the category

OWASP ModSecurity Core Rule Set for application protection; the Elasticsearch/Logstash/Kibana
stack as open-source log correlation with custom dashboards and alerting. Named as examples,
not endorsements.
