## API1 — wrong object

Does every handler taking an ID scope the lookup by the actor? Read, write, and delete? Does the
tenant come from the session, never the request? Does a nested route check the child as well as
the parent? Is there a cross-actor negative test?

Comparing session user ID to request ID covers only directly-owned objects. Shared and delegated
objects need a policy. GUIDs reduce guessing and are not authorization. If the caller should not
reach the endpoint at all, that is API5. ASVS 8.2.2, 8.3.1, 8.4.1.

## API2 — forgeable identity

Enumerate every auth flow: web, mobile, deep link, one-click email, recovery, legacy SDK. Is
recovery throttled like login? Is re-authentication required before changing credentials? Are JWT
algorithm, issuer, audience, and expiry pinned server-side? Do internal services authenticate?

API keys identify client applications and support quota accounting; OWASP says not to use them for
user authentication. Bearer tokens support user sessions and delegated scopes, but whoever captures
one can replay it; self-contained tokens cannot be revoked before expiry. mTLS fits service and
partner identity, at the cost of certificate lifecycle. ASVS V6, V7, V9, V10.

## API3 — wrong field on the right object

Read side: does the response schema cherry-pick fields, or serialize the model and expose private
properties? Write side: does the input schema reject unknown keys, or can one extra key set role,
price, tenant, balance, moderation state, or verification? Review create and update separately.
Do field permissions change with object state?

Object authorization can be correct while property authorization fails. A host may approve their
booking but not set `total_stay_price`; this is OWASP's scenario. Avoid `to_json()` and automatic
client-input binding. Allowlist writes and schema-validate responses. ASVS 8.1.2, 8.2.3.

## API4 — unbounded cost

What hard maximum applies to page size, body and upload size, string and array length, GraphQL
operations per request, memory, process and file descriptor count? Are connect/read/execution
timeouts set? Which calls spend money, and is there a provider cap or billing alert?

Rate limit the verified actor or client, per operation. IP is a pre-auth fallback: NAT shares it
and attackers rotate it. Enforce body size before buffering and page size server-side, not merely
as a default. ASVS 4.2.5, 4.3.1, V2.

## API5 — wrong operation

Can a regular user reach an admin function? Can changing `GET` to `DELETE` perform a sensitive
action? Can group X guess group Y's `/users/export_all`? Do not infer privilege from the URL —
admin operations commonly live in ordinary controllers.

Does the router deny by default per route and method? Do admin controllers inherit a mandatory
check? Search for capabilities (`export`, `impersonate`, `bulk`, `refund`, `sync`), not `/admin`.
Are unused methods blocked, including framework-generated ones? ASVS 8.2.1, 8.4.2, 4.1.4.

## API6 — authorized aggregate attack

Which flows harm the business when a script uses them correctly at scale — purchasing, posting,
reservations, referrals? What business object does the attacker want? Is there a per-actor or
per-instrument cap on that object, not just request count? Is an action free to reverse but costly
to the business, such as booking most seats then cancelling?

Rate limits help and do not solve distributed abuse. OWASP names device fingerprinting, human
detection, non-human sequence analysis, and proxy/Tor controls as friction. Apply equivalent
protection to B2B and developer APIs. Business must define the acceptable policy.

## API7 — server fetches a supplied URL

Where can request input reach an HTTP client, DNS lookup, image/PDF processor, or XML parser? Are
schemes, ports, origins, and media types allowlisted? Redirects off? Every resolved address checked
for non-global ranges? Is the raw response hidden? Is the fetcher network-isolated?

Resolve-then-connect remains open to DNS rebinding when the client resolves again. Pin the validated
IP or use an allowlisting egress proxy, and state the gap otherwise. ASVS V2, V12.

## API8 — misconfiguration

Is TLS on every hop? Are verbs, content types, CORS origins, headers, and error schemas explicit?
Can a caller override `X-Forwarded-*` or a gateway identity header? Do load balancer, proxy, and
backend agree on message framing? Are debug routes and traces absent in every environment?

Use a repeatable hardening process and continuous configuration assessment. ASVS 4.1.1–4.1.4,
4.2.1–4.2.4, V13.

## API9 — unknown surface

Which hosts actually answer, including staging, old versions, regions, and forgotten deployments?
Which deprecated versions remain routable and patched? Does non-production contain production
data? Is documentation generated in CI? Which third parties receive which sensitive fields, and
why?

Inventory hosts by environment, access and version, and inventory integrated data flows. Apply
protection to all exposed versions. Backport security fixes or retire old versions with a measured
migration. Documentation access itself should match its audience.

## API10 — upstream trusted more than users

Is every upstream response schema-validated and size-bounded, with connect and read timeouts? Are
redirect destinations allowlisted? Can upstream data reach SQL, a template, shell, or deserializer
without sink-specific encoding? Does malformed data or a timeout fail closed without partial state?

Use TLS, assess provider security before integration, and treat every response as untrusted input.
ASVS V1, V2, V12.
