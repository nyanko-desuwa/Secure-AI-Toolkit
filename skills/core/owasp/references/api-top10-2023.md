# OWASP API Security Top 10 (2023)

The API list overlaps the main Top 10 but splits authorization into three separate failures,
because that is where API breaches actually happen. Use this list whenever the surface is
REST, GraphQL, gRPC, or a webhook receiver.

Source: <https://owasp.org/API-Security/editions/2023/en/0x11-t10/>

| ID | Category | The question it asks |
|---|---|---|
| API1:2023 | Broken Object Level Authorization | Does the handler check that this actor owns this object ID? |
| API2:2023 | Broken Authentication | Can the caller's identity be forged, replayed, or brute-forced? |
| API3:2023 | Broken Object Property Level Authorization | Can the caller read or write fields they should not see or set? |
| API4:2023 | Unrestricted Resource Consumption | What stops one caller from exhausting CPU, memory, storage, or a paid third-party quota? |
| API5:2023 | Broken Function Level Authorization | Can a regular user reach an admin operation by guessing the route or method? |
| API6:2023 | Unrestricted Access to Sensitive Business Flows | Can the flow be automated at a scale that harms the business, even using it "correctly"? |
| API7:2023 | Server Side Request Forgery | Does the API fetch a URL the caller supplied? |
| API8:2023 | Security Misconfiguration | Are headers, CORS, TLS, and error verbosity correct on every environment? |
| API9:2023 | Improper Inventory Management | Are there older versions, staging hosts, or undocumented endpoints still reachable? |
| API10:2023 | Unsafe Consumption of APIs | Is data from an upstream API trusted more than data from a user? |

## The three authorization failures, distinguished

These get conflated constantly, and the fixes are different.

API1 is the wrong object. `GET /invoices/4192` returns someone else's invoice. Fix: scope the
query by the actor.

API3 is the wrong field on the right object. Two shapes:

- **Excessive data exposure** — the response serializes the whole model, including
  `password_hash` or `internal_notes`. Fix: an explicit response schema, not the ORM object.
- **Mass assignment** — the request body sets `role: "admin"` or `account_balance`, and the
  handler passes the whole dict to the model. Fix: an explicit input schema that rejects
  unknown keys.

API5 is the wrong operation. `DELETE /users/4192` works for a non-admin because only `GET`
had a guard. Fix: deny by default at the router, per method.

## Notes that matter in practice

**API4 and API6 are not the same.** API4 is resource exhaustion — a `limit=1000000` query or
an unbounded file upload. API6 is business abuse at scale — scripted ticket buying, bulk
account creation, scraping every product page. Rate limiting helps both but only solves API4.
API6 needs flow-level controls: proof of work, device fingerprinting, or human review.

**API9 is the one nobody checks.** `api.example.com/v1` stays online for years after `v2`
ships, unpatched. Enumerate what is actually reachable before declaring an audit complete.

**API10 inverts the usual trust model.** A partner API's response is untrusted input. Validate
it, bound its size, set a timeout, and do not follow its redirects blindly.

## GraphQL specifics

The list applies, but the attack surface shifts:

- API4 becomes query depth and complexity. Cap both; a nested query can be a denial of service
- API1 must be enforced per resolver. A field-level resolver that skips the check leaks data
  regardless of the parent query's guard
- Introspection in production is API9. Disable it or accept that the schema is public
- Batched queries multiply rate limit costs. Count operations, not HTTP requests
