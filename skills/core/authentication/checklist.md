# Authentication Verification Checklist

Mark pass, fail, or not applicable. An N/A needs a reason. These checks map to OWASP Top 10
2025 A07 (authentication) or A01 (authorization), ASVS V6-V10, and the CWE shown.

## Passwords and Login — A07 · V6 · CWE-256, CWE-307

- [ ] Passwords use Argon2id; bcrypt is used only where Argon2 is unavailable
- [ ] Argon2id cost is measured on production-class hardware and is not weakened to hide latency
- [ ] Every password hash has a unique salt; no SHA-256, SHA-1, MD5, or encryption is used as a password store
- [ ] A pepper, if used, lives in a vault/HSM outside the password database; rotation cost is documented
- [ ] Password input is not silently truncated; the system accepts at least 64 characters
- [ ] Passwords are checked against a breached/common-password blocklist
- [ ] No arbitrary composition rule or periodic forced rotation is imposed; reset follows evidence of compromise
- [ ] Unknown user and wrong password take the same verification path and return the same response
- [ ] Authentication failures do not reveal whether an account exists, is disabled, or is locked
- [ ] Throttling covers account, source IP, device/fingerprint, and distributed credential-stuffing patterns
- [ ] Lockout cannot be used as an unauthenticated denial-of-service against a victim
- [ ] Passwords, tokens, and request bodies containing them never reach logs

## Sessions and Cookies — A07 · V7 · V3 · CWE-384, CWE-613, CWE-352

- [ ] Session IDs come from a CSPRNG and contain at least 64 bits of entropy; custom IDs use 128 bits
- [ ] The session ID is rotated and the pre-authentication ID destroyed after login
- [ ] Session ID rotation also happens after password/MFA/role changes and impersonation start
- [ ] Logout invalidates server-side state, not just the browser cookie
- [ ] Password change, reset, MFA removal, admin disable, and compromise invalidate relevant sessions
- [ ] Idle and absolute timeouts are enforced server-side; absolute lifetime exists even with activity
- [ ] Session cookies use `HttpOnly` to block script reads, `Secure` to require HTTPS, and explicit `SameSite`
- [ ] `SameSite=Lax` is paired with a CSRF token for state-changing requests; it is not treated as CSRF protection alone
- [ ] Cookie scope is narrow; prefer `__Host-`, no `Domain`, and `Path=/`
- [ ] Session, access, refresh, and reset tokens are not stored in browser localStorage/sessionStorage
- [ ] Sensitive actions require recent authentication or a step-up factor

## JWT and Self-contained Tokens — A07 · V9 · V11 · CWE-347

- [ ] The accepted algorithm is a server-side allowlist, never read from the JWT header
- [ ] Key type and algorithm cannot be confused (for example, an RSA public key is never accepted as an HMAC secret)
- [ ] Signature is verified before claims are trusted
- [ ] `iss`, `aud`, `exp`, `nbf`, and any required subject/tenant claims are validated
- [ ] Key selection is constrained to a trusted issuer/JWKS and safe key IDs; `jku`/`x5u` are not fetched blindly
- [ ] Token scope is checked against the requested action, not just token validity
- [ ] Revocation design is explicit; JWT logout is not claimed to be immediate without server state
- [ ] Refresh tokens rotate, detect reuse, revoke the token family, and are invalidated on password change/logout

## OAuth2 and OIDC — A07 · A06 · V10 · CWE-601

- [ ] Authorization code with PKCE `S256` is used; implicit and password grants are absent
- [ ] `state` binds the browser transaction; OIDC also validates a nonce
- [ ] Redirect URIs use exact registered string matching; no wildcard or loose prefix matching
- [ ] Authorization codes are single-use, short-lived, and bound to the client and PKCE verifier
- [ ] Tokens do not appear in URLs, browser history, referrer headers, or application logs
- [ ] Browser token storage choice is documented; prefer a BFF or secure, HttpOnly cookie session
- [ ] Scopes, issuer, audience, and token endpoint authentication are validated

## MFA and Recovery — A07 · V6 · CWE-308, CWE-640

- [ ] WebAuthn/passkeys are offered for phishing resistance; TOTP is a fallback, not the only option for high risk
- [ ] SMS/PSTN is treated as restricted and weakest; an unrestricted alternative is available
- [ ] MFA enrollment requires an existing authenticated factor and confirmation of the new factor
- [ ] MFA removal and replacement require step-up authentication and alert the user
- [ ] Recovery codes are high-entropy, shown once, stored hashed, and single-use
- [ ] Lost-factor recovery has the same scrutiny as login and does not rely on a weak help-desk bypass
- [ ] Reset and recovery events notify the user through an independent channel

## Password Reset — A07 · V6/V7 · CWE-640

- [ ] Request response is identical whether the email/username exists
- [ ] Reset token is generated by a CSPRNG, is high entropy, single-use, short-lived, and stored hashed
- [ ] Token is not derived from user ID, timestamp, counter, or password hash
- [ ] Token is never logged or placed in analytics/referrer-visible URLs beyond the required link
- [ ] A successful reset invalidates existing sessions, refresh-token families, and prior reset tokens
- [ ] New password passes length and breached-password checks

## Authorization, Impersonation, and Audit — A01 · V8 · V16 · CWE-862, CWE-639

- [ ] Authorization is deny-by-default and enforced server-side at the object and function boundary
- [ ] Actor, tenant, role, and resource are derived or looked up server-side, not trusted from the client
- [ ] RBAC, ABAC, or ReBAC choice is documented; policy rules have one auditable enforcement layer
- [ ] Every read, write, delete, export, and admin action checks authorization
- [ ] Impersonation requires explicit privileged authorization, reason, duration, and a visible banner
- [ ] Impersonation cannot change the operator's own identity or bypass step-up controls
- [ ] Audit logs record actor, effective subject, action, target, reason, outcome, time, and source
- [ ] Authorization-service errors fail closed and produce an observable alert

## Before Returning

- [ ] Tests cover wrong algorithm, wrong issuer/audience, expired token, reuse, fixation, reset replay, and cross-user access
- [ ] Relevant tests and build/compile commands were run and reported honestly
- [ ] Runtime assumptions that could not be verified are stated plainly
