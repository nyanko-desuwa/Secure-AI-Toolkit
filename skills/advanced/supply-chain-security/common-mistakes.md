# Common Mistakes

Failures seen repeatedly in AI-generated and hand-written dependency and pipeline
configuration. Each entry: what it looks like, why it fails, and the fix.

## An internal index added alongside the public one

```ini
index-url = https://pypi.org/simple
extra-index-url = https://pypi.acme.internal/simple
```

Written to "let pip find both". pip gives no priority guarantee between indexes, so a public
package claiming the internal name with a higher version can win. This is dependency
confusion, and it needs no access to your systems at all.

Fix: one index — an internal proxy that decides what public packages it mirrors. See
[best-practices.md](best-practices.md#resolve-from-one-place-you-control).

## Defensive publishing treated as the fix

Registering internal names as empty stubs on the public registry. It is worth doing as a
second layer, and it is not the control: it does nothing for a resolver that prefers the
highest version across indexes, does not cover ecosystems where you cannot claim the namespace,
and breaks the day someone adds a package and forgets the stub.

Fix: fix the resolver, then squat the names as defence in depth.

## A plausible package name nobody checked

An assistant suggests `python-jwt`, `requests-oauth`, or `@types/lodash-es` and it installs
cleanly. Typosquats install cleanly by design — that is the whole attack. Registry search
ranking and download counts can both be manipulated.

Fix: verify the name against the project's own documentation, check that the declared
repository exists and contains the published code, and check publish history. A package
whose first release was last week and whose name resembles one with ten million downloads is
the finding.

## A hallucinated package treated as a recommendation

An assistant writes `pip install huggingface-cli`, an import that matches it, and working-looking
code. This is slopsquatting: the model invented a plausible name, and an attacker can register it
so the install succeeds. Unlike a typo, the suggestion can repeat consistently across users and
runs, which makes the nonexistent name worth claiming.

Fix: package names generated by an LLM are unverified input. Confirm each in the upstream
project's own installation documentation before letting a person or agent install it. A clean SCA
result does not help; a newly registered malicious name has no CVE and no known-good history.

## The manifest reviewed instead of the transitive graph

The reviewer reads 20 direct dependencies and never opens the lockfile. Those 20 commonly resolve
to hundreds of packages, each able to run install hooks with identical privilege. The
`event-stream` incident arrived through a newly added transitive package, not a direct dependency
any consumer chose.

Fix: review the lockfile diff and the full graph. Ask the package manager why each surprising
component exists (`npm ls`, `go mod why`, Gradle `dependencyInsight`). A direct-dependency audit
covers intent; the lockfile covers what executes.

## `npm install` in CI

```yaml
- run: npm install
```

`npm install` resolves fresh and rewrites `package.json` and the lockfile. The build you
tested and the build you shipped can differ, and the lockfile you reviewed stops being
authoritative.

Fix: `npm ci --ignore-scripts`. It requires a lockfile, errors when the lockfile and
`package.json` disagree instead of updating the lock, and never writes to either file.

## Pinned versions treated as pinned bytes

```text
requests==2.32.3
```

A version pin says which release you want. It does not say which bytes you got. Registry
compromise, mirror poisoning, and republishing all survive a version pin.

Fix: hashes. `pip install --require-hashes` fails if any requirement, transitive included,
lacks one — so a partially hashed file cannot smuggle an unpinned dependency through.

## Actions pinned to a tag

```yaml
- uses: actions/checkout@v6
```

A tag is a mutable pointer the action's owner can move, and an action runs in your build with
your token. Compromising one popular action is a compromise of every repository that
references it by tag.

Fix: pin the commit SHA with the version in a trailing comment. The comment is what keeps the
pin readable and updatable.

## `pull_request_target` used to make PR CI "work"

```yaml
on: pull_request_target
permissions: write-all
steps:
  - uses: actions/checkout@v6
    with:
      ref: ${{ github.event.pull_request.head.sha }}
```

Reached for because `pull_request` has no secrets and something in the test suite wanted one.
`pull_request_target` runs in the base repository's context; checking out the PR head there
hands an anonymous contributor your secrets and a write token.

Fix: run untrusted code on `pull_request` without secrets. If a test genuinely needs a
credential, move that test to a job triggered after review, or give it a scoped throwaway.

## Signing without verifying

```bash
cosign sign "$IMAGE"      # in the build pipeline
# ...and nothing, anywhere, runs cosign verify
```

Signing proves who built it only to someone who checks. An unverified signature is metadata.

Fix: verify at the consuming end — deploy job or admission controller — with the expected
identity and issuer pinned, by digest, failing the pipeline on mismatch.

## Verification with a wildcard identity

```bash
cosign verify "$IMAGE" --certificate-identity-regexp '.*' \
                       --certificate-oidc-issuer-regexp '.*'
```

Usually added to get past a failing gate. It now confirms that somebody signed the image and
Sigstore was reachable. Anyone with a GitHub account can satisfy it.

Fix: name the workflow identity and the issuer URL. If they are unstable across branches,
anchor the regex to your repository rather than removing it.

## Rebuilding per environment

```bash
docker build -t acme/api:staging .   # then, later
docker build -t acme/api:prod .
```

Two builds of one commit differ in base image contents, resolved transitive dependencies, and
timestamps. The staging test result does not transfer.

Fix: build once, promote the digest. The signature and SBOM attached to that digest then
describe what is actually running.

## An SBOM generated by scanning the running container

Produces an observation of installed packages, not provenance of what the build consumed. It
misses vendored code, static links, and anything installed and removed in an earlier layer, and
it cannot tell you which registry a component came from.

Fix: generate at build time from the lockfile or build graph, scan the finished artefact as a
second view, attach the result to the artefact digest as an attestation, and make a policy query
consume it. SSDF PS.3.2 asks for provenance data for all components of a release.

## An SBOM generated and never read

The pipeline uploads `sbom.json`, the release stays green regardless of its contents, and nobody
can join the file to a deployed digest. That is archival, not a control. An SBOM is an inventory,
not a vulnerability report, and generation is not verification.

Fix: store it keyed by immutable artefact digest, feed it to an inventory that re-evaluates new
advisories, and make explicit policy failures block release or create an owned, expiring finding.
State the limitation: presence is not reachability.

## A networked build called hermetic

The Dockerfile pins the source commit but runs `apt-get update`, `npm install`, or `go install
@latest` during compilation. The result depends on registry state and time, so an independent
rebuild cannot use the same inputs or distinguish a compromise from normal drift.

Fix: fetch pinned, hash-verified dependencies in a separate retrieval step, then compile with no
network. Normalise timestamps, paths, locale, and archive ordering where the toolchain permits.
Record remaining nondeterminism instead of claiming reproducibility.

## Automerge on everything, immediately

```json
{ "automerge": true, "minimumReleaseAge": null }
```

Fast patching is genuinely good. Applied to production dependencies with no cooldown, it makes
you the fastest consumer of a compromised maintainer account — a bot merges the malicious
release at 03:00 and CI runs its install scripts.

Fix: a short cooldown, automerge limited to dev dependencies, and a separate faster path for
security advisories. See [best-practices.md](best-practices.md#guard-the-update-path).

## Triage by CVSS score

Sorting 47 findings by severity and starting at the top. CVSS describes the vulnerability in
the abstract. It knows nothing about whether your code calls the affected function.

Fix: group by reachability from a request path first, then by severity within the group, and
record the reasoning for anything deferred. A 9.8 reachable only from a test fixture outranks
nothing.

## Dev dependencies dismissed as zero risk

"It's devDependencies, it never reaches production." It reaches developer laptops with SSH
agents and cloud sessions, and CI runners with deploy credentials. The 2025 `Shai-Hulud` npm
worm targeted exactly that environment.

Fix: downgrade the severity, do not dismiss the finding. Anything that executes during install
or test is in scope.

## A malicious package handled as a version bump

Removing the bad version, upgrading, and closing the ticket. If a malicious package executed in
your build, every secret that build could read should be assumed stolen.

Fix: revoke and rotate first, then investigate which builds consumed it, then fix the
dependency. See [troubleshooting.md](troubleshooting.md#a-dependency-turns-out-to-be-malicious).

## A vendored copy that left the dependency graph

Copying a library's source into the repository to avoid an upgrade fight. It now has no
version, no advisory feed, no SBOM entry, and nobody patches it.

Fix: if you must vendor, record upstream URL, exact version or commit, and source hash; preserve
local modifications as reviewable patches; make the component appear in the SBOM; and assign an
owner to monitor upstream advisories. Silent vendoring is CWE-1104 with the evidence removed.
Vendoring trades registry and availability risk for patch ownership — it does not eliminate a
dependency.
