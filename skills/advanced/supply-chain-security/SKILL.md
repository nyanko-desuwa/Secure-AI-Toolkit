# Supply Chain Security

Most of the code you ship, you did not write. `A03:2025 Software Supply Chain Failures` is
new in the 2025 Top 10 — not a renumbering of 2021's A06 Vulnerable and Outdated Components.
It was promoted because the failure has grown beyond known CVEs in libraries to the full process
that builds, distributes, and updates software: dependency resolution, maintainer compromise,
install hooks, developer tooling, registries, CI/CD, provenance, and artifact promotion. It ranked
first in the community survey, with exactly half of respondents placing it #1, and had the highest
average incidence in the contributed data while mapping to only 11 CVEs — a broken build or
poisoned registry usually does not receive a CVE at all.

`A08:2025 Software or Data Integrity Failures` is related but lower-level: it is your consumer
trusting an artifact, update, or critical datum without verifying it. A pipeline that pulls an
unsigned image is A08. A registry configuration that lets an outsider answer to your private
package name is A03.

## When to Use

- Adding, upgrading, or replacing a dependency
- Writing or reviewing a CI/CD workflow, Dockerfile, or release job
- Setting up a registry, mirror, proxy, or artifact repository
- Deciding whether a CVE in a transitive dependency needs action this week
- A dependency turns out to be malicious, or a maintainer account is compromised
- Anyone asks for an SBOM, provenance, or "are we SLSA compliant"

## The Trust Question

Six links. Each one is a place where something you did not write gets to run.

| Link | The question | Control |
|---|---|---|
| Resolution | Could a public package answer to an internal name? | Scoped registry, no fallback. ASVS 15.2.4 |
| Retrieval | Is this the exact bytes we reviewed? | Lockfile with hashes, verified at install |
| Install | Does installing run code? | Disable lifecycle scripts, prefer built artefacts |
| Build | Could one build tamper with another, or with its own provenance? | Isolated hosted builder. SLSA Build L3 |
| Distribution | Who could have replaced this artefact? | Signature bound to an identity, verified at consume |
| Update | What happens when the maintainer is not the maintainer? | Cooldown, review, no auto-merge on privileged deps |

Work the list in order. Signing an artefact built from a confused dependency proves you
faithfully shipped someone else's malware.

## Workflow

### 1. Inventory what you actually consume

Direct dependencies are the ones people read. Transitive ones are where the incidents happen.
Produce the full graph from the lockfile, not from the manifest. ASVS 15.1.2 asks for an
inventory such as an SBOM, and asks you to verify components come from predefined, trusted,
continually maintained repositories.

### 2. Close resolution and retrieval

One index, no fallback, exact versions, hashes checked at install time. Check package names before
adoption, including LLM-suggested names: typosquatting and slopsquatting are name-trust failures,
not SCA findings. See [best-practices.md](best-practices.md#resolve-from-one-place-you-control),
[best-practices.md](best-practices.md#decide-whether-to-add-it-at-all), and
[references/ecosystem-controls.md](references/ecosystem-controls.md).

### 3. Stop install-time execution

`npm postinstall`, Python source builds (`setup.py` and backend hooks), and an explicitly invoked
`go generate` run with the identity and credentials of the installer. The attack lands before
your application code ever runs. The 2025 `Shai-Hulud` npm worm used exactly this path. See
[best-practices.md](best-practices.md#stop-install-time-code-execution).

### 4. Make the build attestable

Hosted builder, no user-controlled step near the signing key, provenance generated by the
platform. That is SLSA Build L2 then L3. Make inputs hermetic and outputs reproducible where the
ecosystem allows it; those detect undeclared build inputs, while provenance records the inputs
and builder identity. See [references/slsa.md](references/slsa.md) and
[best-practices.md](best-practices.md#build-reproducibly-enough-to-compare).

### 5. Sign, then verify on the way in

An unverified signature is decoration. The verify step names the expected identity and
issuer, or it accepts anything anyone signed. See
[best-practices.md](best-practices.md#sign-and-actually-verify).

### 6. Promote artefacts, do not rebuild them

Staging and production consume the same digest. A rebuild is a new artefact with none of the
testing. See [best-practices.md](best-practices.md#promote-by-digest).

### 7. Triage on reachability and a written clock

A CVE in a dev-only transitive dependency is not the same finding as one in a request path.
ASVS 15.1.1 wants documented, risk-based remediation windows; 15.2.1 wants no component past
its window. See [best-practices.md](best-practices.md#triage-and-remediation-windows).

### 8. Verify

Run [checklist.md](checklist.md). Every unchecked box is a fix or a stated limitation.

## Severity

Rank by what executes, where, and with which credentials.

- **Critical** — code from an unverified source executes in CI or production with access to
  secrets or deploy credentials. Dependency confusion on a resolvable internal name, a
  malicious lifecycle script, an unsigned artefact deployed unverified
- **High** — a reachable, exploitable vulnerability in a production dependency; a CI workflow
  where a fork PR can run with a write token; unpinned mutable references in a release path
- **Medium** — unmaintained or unreachable-vulnerable dependency; missing provenance or SBOM;
  no lockfile in a non-release path
- **Low** — a lint-level gap with no execution path. Missing `Scorecard` badge, unpinned
  dev-only tool version

A CVSS 9.8 in a package imported only by a test fixture is not critical. Say why. Conversely
a `postinstall` script in any dependency of any build is critical regardless of CVSS, because
CVSS does not score "runs arbitrary code by design".
