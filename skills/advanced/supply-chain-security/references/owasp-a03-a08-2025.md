# OWASP Top 10 2025 — A03 and A08

> Verified 2026-07-28 against
> <https://owasp.org/Top10/2025/A03_2025-Software_Supply_Chain_Failures/> and
> <https://owasp.org/Top10/2025/A08_2025-Software_or_Data_Integrity_Failures/>

Two categories, one topic, different altitudes. A03 is the process that delivered the
component. A08 is your code trusting an artefact it did not verify. The A08 page says so
directly: it operates "at a lower level than Software Supply Chain Failures".

## A03:2025 Software Supply Chain Failures

New name, position #3. It descends from 2013's "A9 – Using Components with Known
Vulnerabilities" but is deliberately broader than known-vulnerable components.

It came first in the community survey, with half of respondents ranking it #1. The published
figures: highest average incidence rate of any category, 215,248 total occurrences, and only
11 CVEs across its mapped CWEs. That last number is the interesting one — a broken build
process does not produce a CVE, so scanners see almost none of this.

Definition, as published: "breakdowns or other compromises in the process of building,
distributing, or updating software."

### Mapped CWEs

| CWE | Title |
|---|---|
| CWE-447 | Use of Obsolete Function |
| CWE-1035 | 2017 Top 10 A9: Using Components with Known Vulnerabilities |
| CWE-1104 | Use of Unmaintained Third Party Components |
| CWE-1329 | Reliance on Component That is Not Updateable |
| CWE-1357 | Reliance on Insufficiently Trustworthy Component |
| CWE-1395 | Dependency on Vulnerable Third-Party Component |

CWE-1357 is the one to reach for on dependency confusion and typosquatting: the component is
not known-vulnerable, it is not trustworthy. CWE-1329 covers the pinned-forever dependency
you cannot patch — a real finding even with no CVE attached.

Note a discrepancy in the source: the background text cites CWE-477 for obsolete function
use while the mapped list gives CWE-447. Quote the mapped list.

### Exposure conditions worth checking

Paraphrased from the category. These are checkable, unlike the title:

- Component versions not tracked across client and server, including transitive dependencies
- Anything in the stack out of date or unsupported: OS, web/app server, DBMS, APIs, runtimes,
  libraries
- No regular scanning, no subscription to security bulletins for what you use
- No change management across the chain: IDEs and their extensions, code repos, sandboxes,
  image and library repos, artifact creation and storage
- Chain not hardened, particularly access control and least privilege
- No separation of duty, so one person can ship to production unreviewed
- Untrusted-source components used in, or able to reach, production
- Patching not risk-based and timely — monthly or quarterly change windows leave "days or
  months of unnecessary exposure"
- No compatibility testing after an update or patch
- The CI/CD pipeline less secure than the application it builds

The last one is the finding people miss. A hardened application built by a pipeline where any
contributor can add a step is an A03 finding on the pipeline.

### Prevention, as published

Patch management: centrally produce and maintain an SBOM for the whole system; track direct
and transitive dependencies; remove unused dependencies, features, files, and docs; keep a
continuous component inventory (OWASP Dependency-Track, OWASP Dependency-Check, retire.js are
named); monitor CVE, NVD, and OSV continuously with SCA or SBOM tooling; pull only from
official sources over secure links, preferring signed packages; choose versions deliberately;
watch for unmaintained components and migrate or virtual-patch; keep CI/CD, IDEs, and
developer tooling updated; use staged rollouts or canary deployments rather than updating
everything at once.

Change management should track CI/CD settings and build pipelines, code repositories,
sandboxes, developer IDEs, SBOM tooling and artefacts, logging systems, third-party and SaaS
integrations, artifact repositories, and container registries.

Hardening with MFA and tight IAM across code repositories (no checked-in secrets, protected
branches, backups), developer workstations, build servers and CI/CD (separation of duties,
signed builds, environment-scoped secrets, tamper-evident logs), artifacts (provenance,
signing, timestamping, promotion over rebuilds, immutability), and infrastructure as code
(PRs, version control).

### Scenarios, as published

1. A trusted vendor is backdoored and the compromise spreads on upgrade. SolarWinds in 2019
   reached roughly 18,000 organisations.
2. A compromised vendor misbehaves only under specific conditions. The 2025 Bybit theft of
   $1.5 billion came from wallet software that triggered only when the target wallet was in
   use.
3. `Shai-Hulud` (2025), "the first successful self-propagating npm worm". Malicious versions
   of popular packages used post-install scripts to exfiltrate secrets to public GitHub
   repos, then reused any discovered npm tokens to publish further malicious packages. It
   spread past 500 package versions before npm shut it down.
4. Components inherit application privileges. CVE-2017-5638 (Struts 2 RCE) and
   CVE-2021-44228 (Log4Shell) are the cited examples.

Scenario 3 is the one to quote when someone argues that disabling lifecycle scripts is
paranoid. The propagation mechanism was `postinstall` plus a stolen publish token.

## A08:2025 Software or Data Integrity Failures

Position #8, unchanged. The conjunction in the name changed from "and" to "or". Headline CWEs
in the background: CWE-829, CWE-915, CWE-502. 14 CWEs mapped, 3,331 CVEs.

Mapped CWEs: 345, 353, 426, 427, 494, 502, 506, 509, 565, 784, 829, 830, 915, 926.

For supply chain work the useful ones are CWE-494 (Download of Code Without Integrity Check),
CWE-829 (Inclusion of Functionality from Untrusted Control Sphere), CWE-345 (Insufficient
Verification of Data Authenticity), and CWE-353 (Missing Support for Integrity Check).

### What it covers

Infrastructure and code treating untrusted input as trustworthy:

- Plugins, libraries, or modules from unvetted repositories and CDNs
- An "insecure CI/CD pipeline without consuming and providing software integrity checks"
- A pipeline pulling artifacts without signature verification
- Auto-update that fetches without integrity checks, letting an attacker push their own build
  to every install
- Serialized state an attacker can observe and alter

### Prevention, as published

- Verify origin and integrity via "digital signatures or similar mechanisms"
- Restrict npm, Maven, and similar to trusted repositories; higher-risk shops run a vetted
  internal mirror
- Require review of code and configuration changes
- Segregate, configure, and access-control the CI/CD pipeline across build and deploy
- Reject unsigned or unencrypted serialized data from untrusted clients unless integrity
  checks detect tampering or replay

The unsigned-firmware scenario carries a line worth remembering: often "there is no mechanism
to remediate other than to fix in a future version." Design updateability before you need it
— that is the CWE-1329 side of A03 meeting A08.
